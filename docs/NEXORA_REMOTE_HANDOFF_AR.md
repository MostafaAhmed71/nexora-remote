## 1. تعريف المشروع وحالته الحالية

NEXORA Remote منصة ويب لإدارة وصول مصرح به إلى أجهزة Windows، مع مشاهدة الشاشة والتحكم عن بُعد، وعزل المؤسسات والمستخدمين، وسجل تدقيق. أضيف إليها مسار لإدارة المعامل من لوحة ماستر: إدارة أجهزة جماعية، وقت استخدام، باقات، قفل تعاوني، خريطة قاعات، ونقل ملفات بموافقة محلية.

- المستودع: `https://github.com/MostafaAhmed71/nexora-remote`.
- مساحة العمل: `F:\NEXORA Remote`.
- الفرع المحلي: `main`، والـremote الحالي يستخدم HTTPS.
- آخر commit محلي وقت إعداد التقرير: `5dde094dadb9ee47b6d56ef4223e1662fb4ea255` بعنوان `Merge remote-tracking branch 'origin/main'`.
- رقم الإصدار المعلن في `package.json` ومشروع الوكيل والمثبت: `0.3.0`.
- البروتوكول: الإصدار 2.
- إضافات الماستر أحدث من النسخة الموثقة تاريخيًا، ولم يزد رقم الإصدار بسببها بعد.
- توجد ملفات معدلة وأخرى جديدة غير متتبعة. **استنساخ GitHub وحده لا يضمن الحصول على إضافات الماستر الموجودة هنا.** يجب تسليم التعديلات الحالية أو حفظها في commit أولًا، دون فقد الملفات المحلية.
- الوضع: Engineering Preview / نسخة هندسية للتطوير والتحقق، وليست إصدارًا تجاريًا معتمدًا.
- لم يُنشأ نشر إنتاجي أو VPS أو مورد مدفوع ضمن هذا العمل، ولم تُوصَل أجهزة مؤسسية حقيقية.

## 2. ما طلبه صاحب المشروع

اختار المستخدم هذه الإضافات وطلب تنفيذها:

1. نقل الملفات بين الماستر والأجهزة.
2. إدارة أجهزة جماعية.
3. تحديد وقت استخدام لكل جهاز أو مجموعة من جهاز ماستر.
4. وضع الحصة أو الامتحان لتحديد البرامج والمواقع المسموحة.
5. القفل الجماعي.
6. باقات وقت جاهزة ومخصصة.
7. خريطة للأجهزة موزعة حسب القاعة والمكان.

المقصود بالماستر في التنفيذ الحالي هو لوحة الويب بحساب مالك أو مدير، وليس برنامج Windows مستقلًا للماستر. عند انتهاء الوقت، التصور المعتمد في النسخة الأولى شاشة قفل، وليس إيقاف تشغيل كامل. رد المستخدم على اختيار نوع القفل كان تأكيدًا عامًا؛ لا يوجد طلب مؤكد بتنفيذ Shutdown.

**فجوتان مهمتان بين الطلب والتنفيذ:** القفل الحالي تعاوني وليس قفل نظام محصّنًا؛ ووضع الحصة مشغل موجه فقط، ولا يفرض قائمة سماح حقيقية للبرامج والمواقع.

## 3. البنية التقنية

المشروع monorepo بملف npm lock واحد في الجذر.

### الواجهة

- React وTypeScript وVite.
- React Router للتنقل وTanStack React Query للبيانات.
- واجهة عربية RTL، وتنسيق للموبايل، ووضع فاتح وداكن.
- Lucide للأيقونات، وCSS محلي؛ لا يوجد إطار مكونات خارجي مفروض.

### الخادم

- Node.js 24 وFastify 5 وTypeScript.
- WebSocket للبث والإدخال.
- Zod للتحقق من المدخلات.
- PostgreSQL عبر `pg`، ومعاملات مرتبطة بالمؤسسة.
- Argon2id لكلمات المرور، وTOTP للمصادقة الثنائية.
- Cookies وHelmet وRate Limit وSwagger UI.
- `createApp` تفصل إنشاء التطبيق عن نقطة التشغيل، مما يسمح باختباره مباشرة.

### وكيل Windows

- C# و.NET 10 وWindows Forms.
- له وضع مستخدم مباشر، ووضع Windows Service مع عامل تفاعلي منفصل.
- التقاط الشاشة: GDI، ثم JPEG، ثم النقل عبر WebSocket relay.
- الإدخال: Windows SendInput، مع دعم نصوص Unicode.
- حماية الهوية المخزنة باستخدام DPAPI وصلاحيات Windows.

### الاختبارات والبنية المساعدة

- Vitest لاختبارات الخادم والبروتوكول والأمان والشبكة.
- Playwright لاختبارات المتصفح.
- PGlite لقاعدة PostgreSQL مؤقتة داخل الاختبارات والتشغيل التجريبي.
- اختبارات PostgreSQL أصلي منفصلة، وعقود C#، وفحوص Windows أصلية.
- Docker/Compose وNginx موجودة كقوالب تشغيل؛ وجود الملفات لا يعني أن النشر نُفذ أو اختُبر هنا.

## 5. الحسابات والمؤسسات والصلاحيات

المنفذ حاليًا:

- دخول بالبريد وكلمة المرور، وجلسات دخول بملف Cookie من نوع HttpOnly، مع SameSite وSecure في الإنتاج.
- تسجيل خروج، وعرض جلسات الحساب وإلغاؤها.
- إعداد وتأكيد MFA، وتوليد رموز استعادة أحادية الاستخدام ببصمات مخزنة، مع استبدال المجموعة بمعاملة واحدة.
- استعادة كلمة المرور عبر موصل خارجي اختياري؛ إن لم يُضبط الموصل يرجع المسار خطأ بأن التسليم غير مهيأ.
- حساب Platform Administrator لتوفير مستخدمين وإدارة معلومات المنصة؛ هذا منفصل عن مالك مؤسسة. مسار إنشاء مؤسسة متاح للمستخدم المسجل، ويضيفه مالكًا لها، ولا يشترط حاليًا علم Platform Administrator.
- عضويات مؤسسات وأدوار ثابتة: `owner`, `admin`, `technician`, `employee`, `viewer`.
- ACL لكل جهاز، مفعل افتراضيًا، مع صلاحيات تشمل `view`, `control`, `terminate`, `devices`, `files`, `clipboard`.
- مالك المؤسسة ومديرها لهما امتيازات إدارة أوسع؛ الفني يحتاج منح الجهاز المناسبة، ولا يملك إدارة الماستر الزمنية العامة.
- وصول الفني لمسارات الملفات يحتاج صراحة ACL من نوع `files` إلى جانب صلاحية الدور، وليس مجرد صلاحية إدارة الجهاز.
- `clipboard` قيمة صلاحية محجوزة؛ وجودها في البيانات لا يعني أن الحافظة منفذة.
- سجل تدقيق للأحداث؛ عرض السجل الحالي محدود بآخر 200 صف.

مهم: لا يوجد تسجيل عام ذاتي مكتمل للمستخدمين أو نظام دعوات بالبريد. توفير المستخدمين يتم بواسطة مدير المنصة، ثم تُضاف عضويتهم للمؤسسة. واجهة الأدوار تعرض تعريفات ثابتة؛ لا يوجد محرر أدوار مخصصة كامل.

## 6. الأجهزة والاتصال عن بُعد

### إدارة الأجهزة

- تسجيل الجهاز برمز أحادي الاستخدام صالح 10 دقائق ومربوط بالمؤسسة.
- مفتاح RSA عام للجهاز بطول 3072 بت على الأقل في مسار التسجيل.
- عرض اسم الجهاز والنظام وإصدار الوكيل والمجموعة وآخر ظهور وحالة الاتصال.
- التفريق بين «الجهاز متصل» و«سطح المكتب التفاعلي متاح».
- تعديل الاسم والمجموعة، وإدارة ACL، وإلغاء الثقة بالجهاز وإنهاء جلساته.
- الجهاز غير الموثوق لا يحصل على إثبات أوامر جديد.

### مشاهدة الشاشة والتحكم

- وضع مشاهدة ووضع تحكم منفصلان.
- جلسة مرتبطة بالمستخدم والمؤسسة والجهاز وصلاحياته، ومنحة تحكم موقعة حتى خمس دقائق وبما لا يتجاوز جلسة الدخول.
- عارض متصفح مع ملء الشاشة، وملاءمة الحجم، والحجم الفعلي، والتكبير.
- اختيار جودة ودقة وFPS وشاشة، ضمن الحدود المدعومة.
- إدخال ماوس وكيبورد وعجلة ونص Unicode، مع تسلسل لمنع إعادة تشغيل الإدخال.
- عرض معدل استقبال الإطارات والبيانات وزمن RTT إلى الخادم ومدة الاتصال وتوقيتات التقاط/ترميز عند توفرها.
- ACK من المتصفح، وإطار واحد معلق على مستوى gate، وإسقاط الإطارات عند البطء بدل صف غير محدود.
- تعديل تدريجي للجودة والدقة وFPS، وتخطي بعض الإطارات الثابتة مع تجديد دوري.
- إعادة اتصال بتأخير متزايد وعشوائية، وإثبات وتفويض جديدين؛ إعادة الاتصال ليست ترخيصًا تلقائيًا لاستئناف التحكم القديم.

القيود: لا تحكم في UAC أو Secure Desktop أو شاشة تسجيل دخول Windows أو تجاوز صلاحيات البرامج المرتفعة. لا تسجيل فيديو للجلسات، ولا صوت أو مكالمة أو دردشة. انتقالات DPI والشاشات والمفاتيح وIME تحتاج مصفوفة تحقق أوسع.

## 7. بروتوكول الأمان والنقل

### اتصال الشاشة

1. يطلب الوكيل تحديًا قصير العمر ويوقعه بمفتاح الجهاز الخاص.
2. يحصل على تذكرة Socket أحادية الاستخدام، عمرها 15 ثانية.
3. الوكيل يرسلها في Authorization؛ المتصفح يستخدم subprotocol مخصصًا مرتبطًا بالجلسة والـCookie والـOrigin.
4. التذاكر في عنوان URL مرفوضة، والبروتوكول القديم v1 مرفوض.
5. يمنح الخادم تفويضًا بصيغة جسم JSON مرمز Base64url وتوقيع RSA-SHA256 على الجسم.
6. الخادم يعيد فحص صلاحية الجلسة والعضوية والدور والجهاز وACL أثناء الإدخال والبث؛ العامل يتحقق بدوره من المنحة.

حزمة الإطار من الوكيل تحمل UUID جلسة بطول 36 بايت ثم JPEG، وبحد أقصى نحو 2 MiB للحزمة. إعدادات الجودة محدودة في مخططات البروتوكول. قناة IPC المحلية JSON بطول مسبوق، بحد 3 MiB، مع قيود SID والتحقق من PID للجهتين. مفتاح الجهاز الخاص لا يرسل إلى العامل التفاعلي.

**النقل الحالي ليس تشفير وسائط طرفيًا بين المتصفح والجهاز.** الخادم وسيط relay ويستطيع قراءة الصورة، ويستطيع كذلك قراءة الملفات المخزنة لديه. HTTPS/WSS مطلوبان للنشر الفعلي، مع استثناء loopback للتطوير.

## 8. إضافات الماستر بالتفصيل

### 8.1 الإدارة الجماعية

- بحث بالاسم، وتصفية بالمجموعة والقاعة.
- تحديد الظاهر أو اختيار أجهزة بعينها.
- نقل أجهزة إلى مجموعة، وتطبيق وقت أو قفل أو ملف حصة على مجموعة مختارة.
- حد العملية 100 جهاز، مع التحقق من المجموعة كلها قبل الإتمام، وقفل الصفوف بترتيب ثابت، والتراجع عن العملية إذا فشل عنصر.
- هذه ليست منصة أوامر جماعية عامة: لا يوجد تنفيذ سكربتات أو تثبيت برامج أو تحديث نظام جماعي.

### 8.2 الوقت والباقات

- إضافة وحذف باقات، كل منها اسم وعدد دقائق؛ المدى الحالي من دقيقة إلى 10080 دقيقة.
- بدء مدة مخصصة أو باقة، وزيادة الوقت، والإيقاف المؤقت والاستئناف.
- الإيقاف المؤقت يحفظ المتبقي ويقفل الاستخدام.
- «فتح وإلغاء المؤقت» يفتح الحالة المطلوبة ويلغي الموعد والمتبقي؛ ليس مجرد إضافة دقائق.
- عرض الوقت المتبقي، وتحذيرات محلية عند الاقتراب من خمس دقائق ودقيقة بصوت وتغيير النص؛ ليست نافذة إشعار نظام مستقلة متكاملة.
- الموعد والحالة محفوظان في قاعدة البيانات، وتُحفظ حالة موقعة محليًا بـDPAPI لحساب Windows.
- أثناء التشغيل الجاري تُستخدم ساعة رتيبة بجانب الوقت المطلق لمنع تمديد الوقت بمجرد إرجاع ساعة النظام.
- توجد استعادة من الحالة المحلية عند بدء الإدارة دون الحاجة إلى اتصال ناجح أولًا، لكن دورة reboot/WTS الفعلية على جهازين لم تُثبت هنا.

### 8.3 القفل الجماعي

القفل المنفذ نافذة TopMost تغطي مساحة سطح المكتب وتعرض انتهاء الوقت أو طلب التواصل مع الماستر. يحتاج تفعيل موافقة الإدارة محليًا على حساب Windows.

**ليس LockWorkStation، وليس Shutdown، وليس كشكًا محصنًا.** لا يُعطل Task Manager أو شاشة الأمان، ولا يمنع المستخدم المحلي من سحب الموافقة. المستخدم المتقدم أو المسؤول المحلي يستطيع تجاوز هذا النمط. لا يُقدّم كحل لمنع التحايل أو لتحصيل وقت مدفوع أو لضبط امتحان حساس.

### 8.4 خريطة الأجهزة

- قاعات مستقلة عن المجموعات المنطقية.
- اسم قاعة وإحداثيا صف وعمود من 0 إلى 20 وملاحظات لكل جهاز.
- عرض الأجهزة بألوان للحالة المطلوبة وعدم اتصال الإدارة، مع الوقت المتبقي.
- منع حجز موضع واحد لجهازين داخل القاعة نفسها، وتحرير المواضع الخاصة بالأجهزة الملغاة عند إعادة تخصيصها.
- الخريطة يدوية الإعداد؛ لا اكتشاف تلقائي للمكان ولا خريطة شبكة أو طوبولوجيا.
- الواجهة تعرض «بانتظار التطبيق» أو «تم التطبيق» وخطأ الوكيل، لأن قبول الخادم للطلب لا يثبت تنفيذه على الجهاز.

### 8.5 وضع الحصة أو الامتحان

يمكن حفظ ملف تعريف باسم، وقائمة مسارات exe كاملة، وقائمة مواقع HTTPS، وتطبيقه على الأجهزة. تظهر للمستخدم أزرار لتشغيل البرامج وفتح المواقع.

**النسخة الحالية مجرد مشغل موجه:** لا تغلق البرامج الأخرى، ولا تفرض قائمة سماح على Windows، ولا تمنع تنقل المتصفح إلى موقع آخر، ولا تمنع الخروج من الحصة. الحظر الحقيقي وسياسات الكشك والمتصفح والبرامج ما زالت مطلوبة لاستيفاء الطلب الأصلي بالكامل.

### 8.6 مزامنة الماستر

- مسار HTTP مستقل عن منح الشاشة القصيرة، والمزامنة الافتراضية نحو كل ثانيتين ما دامت دورة الطلب ناجحة.
- تحدٍ أحادي الاستخدام؛ يوقع الوكيل `nonce + newline + payload`، ما يربط التوقيع بكامل الطلب.
- رد موقع من الخادم ومربوط بالجهاز والمؤسسة والتحدي، وصلاحية رد الشبكة دقيقة تقريبًا.
- حقول `revision`, `agent_revision`, `agent_seen`, `agent_error` لتتبع الحالة المطلوبة وتأكيدها.
- التحقق من التوقيع في مسار العامل قبل التطبيق، مع تخزين محلي للحالة.
- هذا لا يوفر حماية كاملة ضد تعديل مسؤول محلي للساعة أو حذف/إرجاع ملفات الحالة أو إعادة تشغيلها بصورة عدائية.

## 9. نقل الملفات

### من الماستر إلى الجهاز

يختار الماستر ملفًا من صفحة `/master`، ثم يخزن الخادم محتواه في قاعدة البيانات ويقدمه في أجزاء للوكيل. يضغط المستخدم محليًا Accept أو Reject. بعد القبول يحفظ الوكيل الملف في مجلد `NexoraRemote Inbox` داخل مجلد المستخدم، باسم يتضمن معرف النقل لتجنب التصادم.

### من الجهاز إلى الماستر

يختار المستخدم الملف بنفسه من نافذة الإدارة المحلية. يرفعه الوكيل على أجزاء، ثم يستطيع الماستر تنزيله بعد اكتماله. لا يوجد تصفح عن بُعد للقرص، ولا سحب ملف خفي دون اختيار المستخدم.

### الحدود والخصائص

- 10 MiB للملف، و50 MiB وحصة 100 ملف محتسب لكل جهاز؛ الحصص تستثني المنقولات الملغاة أو المرفوضة في الحساب الحالي.
- حجم الجزء 24576 بايت، والمحتوى مرمز Base64 أثناء الطلبات.
- حالة وتقدم وإلغاء، ودعم لإعادة طلب أجزاء الرفع دون مضاعفة المحتوى.
- حالات: `pending`, `complete`, `cancelled`, `rejected`؛ واتجاه `to_device` أو `from_device`.
- صلاحية الوصول للملف 24 ساعة. تنظيف الصفوف المنتهية يجري عند رفع أو مزامنة لاحقة بالمؤسسة، وليس عامل حذف زمنيًا مستقلًا.
- لا تنفيذ تلقائي للملفات، ولا استئناف مضمون بعد إعادة تشغيل الوكيل أو الخادم؛ تقدم الاستقبال المحلي موجود في ذاكرة العملية.
- لا تشفير طرفي للملفات ولا فحص مضاد فيروسات مدمج أو بروتوكول نقل كبير عالي الكفاءة.
- كل تنزيل جديد يحتاج تحقق الجلسة والمؤسسة وصلاحية الملفات.
- **زر الملفات في `Viewer.tsx` ما زال معطلًا ويقول إن النقل غير متاح؛ المسار الفعلي الجديد هو لوحة الماستر.** يلزم توحيد الواجهة والتوثيق لاحقًا.

## 10. قاعدة البيانات

المهاجرات مرتبة ويشغلها `npm run migrate` بمعاملة وقفل advisory، ويتتبع `schema_migrations` الإصدارات المطبقة.

- `001_initial.sql`: المؤسسات والمستخدمون والأدوار والصلاحيات والعضويات وجلسات الدخول والاستعادة والمجموعات وتسجيل الأجهزة والأجهزة والجلسات البعيدة وصلاحياتها والتدقيق وإصدارات الوكيل والخطط والاشتراكات.
- `002_security.sql`: تفعيل ACL افتراضيًا، وجدول `device_acl` ورموز استعادة MFA.
- `003_device_operations.sql`: إضافة صلاحيات إنهاء الجلسات وإدارة الأجهزة ضمن قيم ACL.
- `004_master_management.sql`: جداول `time_packages`, `classroom_profiles`, `device_management`, `managed_files` والفهارس وسياسات RLS.

جداول المؤسسة تستخدم Row-Level Security مع FORCE RLS وربط `app.org_id` داخل معاملة. يعمل الخادم بحساب مقيد لا يملك SUPERUSER أو BYPASSRLS؛ تُشغل المهاجرات وbootstrap بحساب مالك منفصل. توجد علاقات مركبة تمنع ربط بيانات جهاز بمؤسسة أخرى.

بيانات الملفات من نوع bytea داخل قاعدة البيانات؛ التصميم مناسب للحدود الصغيرة الحالية ويحتاج إعادة تقييم للتوسع. presence والتذاكر والـWebSocket والتحديات في ذاكرة عملية الخادم، وليست موزعة بين نسخ متعددة.

## 12. إعداد البيئة والتشغيل

### المتطلبات

- Node.js 24 وnpm.
- PostgreSQL 17 للتشغيل الدائم.
- .NET 10 SDK للبناء، وWindows لاختبار الوكيل التفاعلي.
- نسخة الوكيل المنشورة self-contained لا تحتاج تثبيت runtime منفصل؛ بناء التطوير framework-dependent يحتاج بيئة التشغيل المناسبة.

### إعدادات `.env.example`

- `DATABASE_URL`: اتصال PostgreSQL بحساب التطبيق المقيد.
- `ORIGIN`: أصل المتصفح الدقيق، مع تطابق localhost أو 127.0.0.1 والمنفذ؛ اختلافه يؤثر على فحص origin.
- `PORT`, `HOST`: منفذ وربط الخادم؛ الافتراضي loopback.
- `NODE_ENV`: التطوير أو الإنتاج.
- `MFA_KEY`: مفتاح عشوائي 32 بايت ممثل بست عشري، ولا يوضع في Git.
- `SIGNING_KEY_FILE`, `PUBLIC_KEY_FILE`: مسارا مفتاح توقيع الخادم ومفتاحه العام.
- `RESET_DELIVERY_URL`, `RESET_DELIVERY_BEARER`: موصل HTTPS اختياري لتسليم رابط الاستعادة.

المتغيرات الإضافية المستخدمة أثناء التهيئة أو الاختبار:

- `BOOTSTRAP_EMAIL`, `BOOTSTRAP_PASSWORD`: إنشاء مدير المنصة الأول، بكلمة مرور 12 حرفًا على الأقل وفي قاعدة فارغة فقط.
- `DB_MIGRATION_PASSWORD`: مطلوب لقالب PostgreSQL في Compose.
- `TEST_DATABASE_URL`: قاعدة اختبار PostgreSQL مؤقتة.
- `E2E_ORIGIN`, `E2E_PORT`: أصل loopback ومنفذ مشغل الاختبار.
- `NEXORA_API_TARGET`: هدف proxy الخاص بخادم Vite أثناء التطوير.
- `CHROMIUM_EXECUTABLE`: اختياري لاختيار متصفح لاختبارات Playwright.
- `LOG_LEVEL`: مستوى تسجيل الخادم.

**نقطة تشغيل مهمة:** `apps/server/src/main.ts` لا يقرأ `.env` تلقائيًا. نسخ `.env.example` إلى `.env` وحده لا يكفي؛ يجب حقن المتغيرات في بيئة العملية أو اعتماد طريقة تحميل صريحة لاحقًا.

### التشغيل الدائم للتطوير

```text
npm ci
npm run migrate
npm run bootstrap
npm run dev
npm run dev:web
```

هذه الأوامر ليست متتابعة بلا إعدادات: شغّل قاعدة البيانات، اضبط حساب المهاجرات، وطبّق دور التطبيق وفق `infrastructure/local/app-role.sql`، ثم نفّذ bootstrap على قاعدة فارغة، ثم شغّل الخادم ببيئة حساب التطبيق المقيد ومفاتيح التوقيع وMFA الناتجة. راجع `docs/DEVELOPMENT.md` قبل التنفيذ.

bootstrap يولد مفاتيح تطوير تحت `artifacts/keys` عند عدم وجودها؛ مفاتيح الاختبارات المؤقتة لا تستخدم في النشر.

### التشغيل التجريبي الذي استُخدم محليًا

```powershell
# الطرفية الأولى — قاعدة مؤقتة وواجهة API
$env:E2E_ORIGIN = 'http://127.0.0.1:5180'
$env:E2E_PORT = '3001'
node --import tsx tests/e2e/harness.ts

# الطرفية الثانية — واجهة الويب
$env:NEXORA_API_TARGET = 'http://127.0.0.1:3001'
npm run dev:web -- --port 5180 --strictPort
```

الرابط المحلي: `http://127.0.0.1:5180/master`. استخدم 5180 لأن 5173 كان يشغله مشروع آخر؛ لا توقف أي عملية قبل معرفة مالكها. وقت إعداد التقرير كانت المنافذ 3000 و3001 و5173 و5180 مستمعة؛ هذه ملاحظة تشغيلية وليست ضمانًا لاستمرار العمليات.

المشغل التجريبي ينشئ حساب fixture باسم `e2e@example.test` ومؤسسة `E2E Test Organization`؛ كلمة مروره معرّفة في `tests/e2e/harness.ts`. ليس حسابًا إنتاجيًا ولا ترسل بياناته كأسرار فعلية. البيانات والمفاتيح مؤقتة وتُعاد تهيئتها عند إغلاق العملية وتشغيلها، وقد يلزم تسجيل الدخول واختيار المؤسسة من جديد.

### تفعيل إدارة جهاز Windows

- ابنِ الوكيل المحدث أو استخدم حزمة البناء المحلي، ثم سجّل جهازًا مصرحًا به برمز المؤسسة.
- عنوان السيرفر يجب أن يكون origin فقط، وHTTPS خارج loopback.
- شغّل الخدمة أو فعّل اتصال وضع المستخدم.
- فعّل الموافقة في نافذة `NEXORA — Master management (local consent)` على حساب Windows الحالي.
- راقب تأكيد التطبيق في لوحة الماستر. ظهور الجهاز وحده لا يعني تفعيل الإدارة أو قبول المستخدم للملفات.

أوضاع الوكيل تشمل `--service`, `--worker`, `--configure-service` وأوامر تثبيت/تشغيل/إيقاف/إزالة الخدمة. إدارة خدمة Windows تحتاج موافقة وصلاحيات المسؤول المعتادة.

### الأدلة التاريخية

تقارير المرحلة الثالثة تشير إلى commit تنفيذي `6c3fdaa3dde3577c61b3aaff6f7d8acb3f1f7599` وتشغيل GitHub Actions رقم `40221447469`. هذا مرجع محفوظ في ملفات المستودع؛ لم أتحقق من حالة الرابط على GitHub أثناء كتابة هذا التقرير، ولا يجوز نسب أدلته إلى تعديلات الماستر المحلية.

التقارير التاريخية تشمل فحوص capture/input حقيقية على Windows وloopback، وIPC/DPAPI، وخدمة ومثبت وترقية 0.2 إلى 0.3، واختبارات RLS على PostgreSQL وشبكة netem. نطاقها ليس اتصال جهازَي Windows مستقلين عبر TLS ولا reboot كاملًا لهوية آلة مسجلة.

### قياسات الأداء التاريخية وحدودها

## 15. فروق وتعارضات يجب أن يعرفها المساعد

هذه ملاحظات من قراءة الكود والإعدادات، وليست نتيجة تدقيق أمني شامل:

1. رقم الحزمة والوكيل والمثبت 0.3.0، بينما تذييل الواجهة ما زال `ENGINEERING PREVIEW · 0.1`.
2. `/platform/settings` يرجع `serviceMode: false` رغم وجود تنفيذ خدمة Windows؛ يحتاج تعريفًا موحدًا للقدرات.
3. `/platform/settings` يرجع نقل الملفات متاحًا، بينما زر العارض ما زال معطلًا. يجب توجيه المستخدم إلى نقل الملفات الفعلي أو دمجه بالعارض.
4. بعض وثائق البروتوكول والتقارير القديمة تقول إن الملفات غير منفذة؛ هذه صحيحة تاريخيًا لمسار الشاشة القديم، لكنها لا تصف مسار إدارة الملفات الجديد. وثيقة الماستر هي المرجع للإضافة الجديدة.
5. قالب `infrastructure/docker/nginx.conf` يحدد `client_max_body_size 64k`، بينما مسار رفع ملفات الماستر يقبل جسمًا أكبر حتى 15 MiB لملف 10 MiB مرمز. **من المتوقع أن يمنع القالب رفع ملفات أكبر من حده إن استُخدم كما هو.** لم يُختبر هذا النشر هنا، ولم أعدل القالب ضمن إعداد التقرير.
6. `.env.example` قالب فقط ولا يُحمل تلقائيًا في نقطة تشغيل الخادم.
7. الخطط والاشتراكات وإصدارات الوكيل لها جداول ومسارات عرض، لكنها ليست منظومة فوترة أو بوابة دفع أو تحديث تلقائي مكتملة. لا تعتبر وجود الصفحة إثباتًا لإنفاذ جميع حدود الاشتراك.
8. رسائل Zod العامة تظهر أحيانًا `Invalid request`؛ بعض النماذج تعتمد إدخال معرفات يدويًا. مشكلة طلب بيانات قبل اختيار المؤسسة عولجت في مكون عرض البيانات، لكن لا يوجد ادعاء بأن كل التدفقات صارت موجهة بالكامل.
9. الواجهة العربية والملاحظات التشغيلية الإنجليزية في الوكيل تحتاج توحيدًا لغويًا.
10. استئناف الملفات عبر إعادة تشغيل العمليات، والتنظيف الدوري المستقل، وتوسيع حدود وحماية نقل الملفات، ما زالت مجالات تطوير.

## 16. ما لم يُنفذ أو لم يكتمل بعد

### غير منفذ

- قائمة سماح ملزمة للبرامج والمواقع أو كشك امتحان آمن.
- قفل Windows مقاوم للتحايل مرتبط بالوقت، أو إيقاف تشغيل مؤكد عند انتهاء المدة.
- مزامنة الحافظة.
- تسجيل جلسات الشاشة، والدردشة والصوت.
- دعوة دعم سريع مستقلة بكود سهل للمستخدم.
- Wake-on-LAN، وجدولة مهام، وتنفيذ أوامر وتثبيت برامج جماعي.
- نظام تذاكر دعم، وبوابة عميل مكتملة، وتنبيهات تشغيلية متكاملة.
- فواتير ومدفوعات وحساب رصيد أو تسعير تجاري للوقت.
- محرك WGC/DXGI أو H.264 أو WebRTC.
- تشفير وسائط/ملفات طرفي، أو relay موزع متعدد العقد.
- Code Signing وتحديث تلقائي موثوق وrollback تلقائي وتدوير مفاتيح سلس.

### موجود جزئيًا أو يحتاج تحققًا أوسع

- خدمة الآلة والعامل التفاعلي: الكود موجود، لكن المسار الكامل بعد تسجيل آلة وreboot وتبديل المستخدم والقفل/الخروج لم يُثبت هنا على جهازين.
- تعدد الشاشات وتغير DPI والدقة واختصارات الكيبورد وIME.
- استقرار لساعات طويلة وقياسات WAN وحمل relay وحدود CPU/RAM/عدد الأجهزة.
- توصيل مزود استعادة الحساب في بيئة فعلية.
- احتفاظ وتصدير سجلات التدقيق، ومراقبة وإنذارات، ونسخ احتياطي مع تجربة استرجاع.
- مراجعة أمنية مستقلة، خاصة امتيازات الخدمة وحدود الثقة وتنفيذ إدارة الوقت والقفل.

## 17. متطلبات الانتقال إلى تشغيل فعلي

هذه خطة استكمال وليست أعمالًا نُفذت:

1. حفظ التعديلات المحلية ومراجعتها، وتوحيد رقم الإصدار والقدرات والتوثيق.
2. فصل التشغيل الدائم بقاعدة PostgreSQL عن مشغل PGlite التجريبي.
3. اختبار جهازين Windows مصرح بهما، مع HTTPS/WSS، والخدمة والعامل والموافقة المحلية.
4. اختبار انقطاع الاتصال وإعادة تشغيل السيرفر والوكيل والجهاز، والقفل والخروج وتبديل المستخدم.
5. تحديد معنى القفل المطلوب بدقة، وإصدارات Windows والحسابات المستهدفة وسياسة الاسترداد قبل تنفيذ عزل نظام حقيقي.
6. تنفيذ الحظر الحقيقي لوضع الامتحان بطريقة مناسبة لإصدارات Windows والمتصفح، مع مسار خروج واسترداد إداري واضح.
7. تجربة نقل الملفات وقبولها ورفضها وإلغائها على أجهزة فعلية، وتصحيح reverse proxy وحدوده، وقياس السرعة والذاكرة.
8. تشغيل PostgreSQL integration والمثبت والترقية والاختبارات الأصلية على التعديلات الجديدة، وCI جديد مربوط بcommit محدد.
9. إدارة أسرار وشهادات TLS، وتوقيع المثبت، ونسخ احتياطية واسترجاع، ومراقبة وحدود حمل وخطة فشل.
10. الاحتفاظ بخادم واحد أولًا؛ التوسع الأفقي يحتاج shared state وتوجيه relay صحيحًا، وليس إضافة load balancer فقط.

## 18. تعليمات تسليم مباشرة للمساعد التالي

أنت تستكمل مشروع NEXORA Remote الموجود؛ لا تبدأ مشروعًا بديلًا، ولا تستبدل البنية الحالية دون سبب واضح. اقرأ `git status` واحتفظ بالتعديلات غير الملتزم بها؛ ملفات الماستر الجديدة قد لا توجد على GitHub بعد.

ابدأ بهذه المراجع:

1. هذا التقرير و`README.md`.
2. `docs/MASTER_MANAGEMENT_AR.md` و`docs/FEATURE_IDEAS_AR.md`.
3. `apps/server/src/management.ts` و`apps/web/src/MasterConsole.tsx`.
4. `Management.cs` و`TimeBudget.cs` و`SessionBroker.cs` و`DesktopWorker.cs` في الوكيل.
5. المهاجرات الأربع واختبارات الإدارة والمتصفح وعقود C#.
6. `docs/PROTOCOL.md`, `docs/DEVELOPMENT.md`, `docs/DEPLOYMENT.md` وتقارير الجاهزية التاريخية، مع الانتباه إلى تواريخها ونطاقها.

حافظ على عزل المؤسسات، والفحص الحي للصلاحيات، والتوقيع، والموافقة المحلية، وعدم إرسال المفاتيح الخاصة للعامل. لا تحول تشغيل fixture المؤقت إلى إعداد إنتاجي، ولا تنسب CI قديمًا إلى كود جديد، ولا تعتبر صور الشاشة أو نجاح الحفظ إثباتًا لقفل Windows فعلي. أثبت أي ادعاء جديد باختبار له النطاق نفسه.

لم يُطلب نشر عام أو إرسال رسائل للآخرين أو الاتصال بأجهزة خارجية. إذا انتقلت إلى تلك الأعمال فاستند إلى تفويض المستخدم الفعلي. صاحب المشروع يفضل التنفيذ المباشر والتواصل بالعربية، مع تقرير واضح عما تم وما بقي.

**توصيف التسليم الدقيق:** نواة فعلية لمشاهدة وتحكم Windows مصرح به، مع إدارة متعددة المؤسسات وإضافات ماستر محلية قابلة للاختبار. إدارة الوقت والملفات لها كود واختبارات، لكن القفل غير محصّن ووضع الامتحان الملزم غير منفذ، والتحقق الميداني على جهازين والتجهيز الإنتاجي ما زالا مطلوبين.
